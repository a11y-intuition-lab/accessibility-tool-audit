How do automated accessibility checkers compare?

The Government Digital Service (GDS) ran an audit to see what issues the different accessibility testing tools pick up. GDS deliberately introduced {{ analysis.totals.total }} accessibility barriers to a page of content, and ran them through {{ analysis.counts | length }} automated tools. GDS also had a look at features like usability and cost.

You can use the GDS audit to help choose the best accessibility testing tool for your service.

The original project is available on GitHub. This copy, maintained by {{ copyInfo.org.name }} (AIL), is also on GitHub, and AIL welcomes contributions.

What GDS found

GDS scored each tool for two things.

The first column of numbers shows the percentage of barriers that each tool fully detected on a ‘pass’ or ‘fail’ basis.

The best performing tool in this category found {{ analysis.scoreboard.by_error_warning[0].error_warning }}% of the problems GDS introduced. Whereas the worst performing tool only picked up {{ analysis.scoreboard.by_error_warning[analysis.scoreboard.by_error_warning.length - 1].error_warning }}% of the barriers.

The second column of results takes into account potential barriers that tools noticed, but needed a human being to check, like whether alt text descriptions were accurate. A tool that flags things like this can help you pick up more issues overall.

The best performing tool in this category picked up {{ analysis.scoreboard.by_error_warning_manual[0].error_warning_manual }}% of the deliberate mistakes.

With an AI check

For the test cases neither tool finds, AIL wrote {{ ai.checks }} test procedures an AI model can follow, based on the manual checklist in sa11y, an internal tool. A script collects evidence from each page, such as the HTML, a screenshot, the Tab order and what happens on hover, zoom and Escape, and {{ ai.model }} judges it against the procedures. The model is not told which test case it is looking at.

Of the {{ ai.missed.tested }} test cases neither axe-core nor pa11y finds, the AI check found the intended barrier in {{ ai.missed.confirmed }} ({{ ai.missed.confirmed_percent }}%). On {{ ai.described_in_text }} test pages the barrier is also described in the text of the page, which may help the model. Without them, it found {{ ai.missed_not_in_text.confirmed }} of {{ ai.missed_not_in_text.tested }} ({{ ai.missed_not_in_text.confirmed_percent }}%). On {{ ai.controls.tested }} control pages with no known barrier, it reported a barrier on {{ ai.controls.error }} and a possible barrier on {{ ai.controls.manual }}.

How do features compare?

GDS also compared features like how easy tools are to use, cost and technical considerations - all important things to think about when you are choosing a tool.

What these features mean

Cost

  • Cost (manual) The cost of running the tool manually in a web browser. Paid tools will usually let you check single pages for free, but will redirect you to a login page for some features like documentation.
  • Cost (CI) The cost of running the tool if you code it into your service under continuous integration (CI). Some tools are free to run but you have to pay for features like API access.

Development model

  • Open source The tool is open source, which means you can access the source code for free. You may also be able to help to make the tool better if you can fix a problem with the code.
  • Active The tool is being actively developed. GDS recommends using tools that are updated according to the latest developments in accessibility.

Technical features

  • CI The tool can be run under continuous integration (CI). This is the practice of constantly releasing and testing code. Projects using a CI environment should use an automated testing tool that works with CI. This will help you make sure mistakes in your build are caught early.
  • CLI The tool can be run on a command line interface (CLI). CLI tools are more versatile for developers, and can usually be integrated into either continuous integration (CI) or unit testing.

Usability

  • In-browser The tool works in a web browser. These tools are usually extensions and are easy to install and use, making them useful for non-developers. In-browser tools often make it easier to test things like individual scenarios and internal tools behind firewalls.
  • Internal use The tool can be used internally. This might be useful if your service is for internal use only or has sensitive components that you don’t want to test on the internet.
  • Mobile The tool can simulate a mobile browser and test with it.
  • Scriptable To simulate things like filling in a text box or clicking a button you can write a script for the tool to follow, saving you a lot of manual work.
  • HTTP Auth The tool can access and test password protected websites.
  • Guidance The tool provides related documentation that explains why the thing it has picked up is a problem and how to fix it.
