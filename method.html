How AIL made this copy: method and use of AI Not by GDS

This page describes the work A11y Intuition Lab (AIL) did in this copy of the audit after the Government Digital Service (GDS) finished theirs. It is written so that the work can be checked and repeated. GDS did not carry out, review or endorse any of it.

Summary

  • Original (GDS, 2016 to 2018): 142 test cases and the results for 13 tools, found by people running each tool by hand. These are kept unchanged.
  • Added (2026-10-01): 52 test cases for WCAG 2.0, 2.1 and 2.2 success criteria up to level AAA (30 at level A or AA, 22 at level AAA), and a retest of all 194 test cases with axe-core 4.13.0 and pa11y 10.0.0.
  • Also changed: the build tools were replaced so the project can be built and run safely today.
  • How: the work was done by one maintainer from AIL together with the AI coding assistant Claude Code in a single working day.

Neither part is free of errors. The original results were recorded by people and may contain mistakes. The additions were largely written by an AI and have not yet been fully reviewed. See limitations.

Why AI was used

The original audit has not been updated since 2018. It does not cover the success criteria added in WCAG 2.1 and 2.2, or many AAA criteria. Writing a test page for each missing criterion, modernising an eight-year-old build and running the tools again would not have been possible with the time available. Using AI made it possible to add the missing scenarios and run the retest. Decisions on scope and publication, and the responsibility for the result, stayed with AIL.

The assistant was Claude Code with the model Claude Opus 5.5 (Anthropic), used on 2026-10-01. The instructions given and the decisions made are recorded in the process log. The log is a summary, not a full transcript, but it includes every instruction AIL gave, word for word.

Making the project safe to build

  • At the very start, before AIL said the old code should not be run, the assistant installed the old dependencies once to run npm audit. It also tried the old build, gulp generate. Package install scripts were already turned off on the machine, so no package code ran during the install. The gulp build stopped with an error when it started, because gulp 3 does not work with current Node.js.
  • After that, AIL set the rule that the old code must not be run, and none of it was. All packages were replaced or upgraded. The build now uses npm scripts, nunjucks and Dart Sass. Python and gulp (and node-sass, which needed Python) are no longer needed.
  • npm is configured with ignore-scripts=true in the project, so no package install scripts run. Only package versions at least 7 days old were installed. The package lock file points to the public npm registry.
  • The old dependency tree had 32 known vulnerabilities, 4 of them critical. After the update, npm audit reports none.
  • The generated pages were compared with the old ones to check that the original content was not changed by the new build.

How the added test cases were made

  • AIL compiled a list of success criteria with no test case in the original audit: 1.2.4, 1.2.6, 1.2.7, 1.2.9, 1.3.4, 1.3.5, 1.3.6, 1.4.2, 1.4.5, 1.4.7, 1.4.9, 1.4.12, 2.1.3, 2.1.4, 2.2.3, 2.2.4, 2.2.5, 2.2.6, 2.3.2, 2.3.3, 2.4.1, 2.4.5, 2.4.8, 2.4.11, 2.4.12, 2.4.13, 2.5.1, 2.5.2, 2.5.3, 2.5.4, 2.5.6, 2.5.7, 3.1.3, 3.1.6, 3.2.1, 3.2.3, 3.2.4, 3.2.6, 3.3.4, 3.3.5, 3.3.6, 3.3.7, 3.3.8, 3.3.9 and 4.1.3. Test cases were also added for 1.4.11, 1.4.13 and 2.5.8, which the original covered only partly or not at all.
  • Each test page contains one known failure of one success criterion and as little else as possible. This follows the rule used by GDS: “testing for one specific issue is easier and more reliable to test for.”
  • Claude Code wrote the pages from its knowledge of WCAG 2.2, the Understanding documents and the documented failure techniques. The pages were not checked line by line against these documents by a person.
  • Each added test case records its criterion, level and WCAG version in tests.json (the wcag field). On the test cases page they are marked “Added” and can be filtered by level.
  • Some criteria cannot be shown with one static page, for example consistent navigation across pages (3.2.3, 3.2.4, 3.2.6). These use extra pages in example-pages/. “Live” media is shown as a recorded file labelled as live, because a static page cannot stream.
  • The media files in assets/test_media/ were generated for these test cases. The speech was made with espeak-ng (British English voice). The “background music” is a chord of sine tones about as loud as the speech. The video is an ffmpeg test pattern with the speech as its sound. The commands are in the process log.
  • The 142 original test cases and their results were not changed. The GDS text on the site was only adapted to say “GDS” where it said “we”, so it is clear who did what. The two test cases for 4.1.1 Parsing got a note that this criterion was removed in WCAG 2.2.

How the retest was run

Every test page was opened as a local file in headless Chrome and checked by both tools, one page at a time.

From findings to results

  1. An empty test page, tests/_baseline.html, is checked first. Any finding that also appears on it comes from the page template and is removed from every test page. The example pages have their own structure, so for them any rule that fires on example-pages/_baseline.html is removed. That page has the same structure as the example pages, without a barrier.
  2. axe: any violation gives “issue found”. Otherwise, any incomplete result (“needs review”) gives “user to check”. Otherwise the result is “not found”.
  3. pa11y: any error gives “issue found”. Otherwise, any warning gives “user to check”, in the same way that GDS counted HTML_CodeSniffer warnings as manual checks from April 2018. Notices are ignored because they appear on almost every element.
  4. The percentages are calculated in the same way as the original: the share of test cases with “issue found” or “warning only”, and with “user to check” added.

Repeating the retest

With Node.js 22.13 or later and Google Chrome installed:

git clone https://github.com/a11y-intuition-lab/accessibility-tool-audit.git
cd accessibility-tool-audit
git checkout 02b1e1d
npm ci
npm run build
npm run retest -- --force

npm ci installs the exact package versions in package-lock.json. Set CHROME_PATH if Chrome is not at /usr/bin/google-chrome. The script writes proposals to retest.json and raw findings to results/<date>/. The raw findings from 2026-10-01 are in results/2026-10-01/: every finding per test page for each tool, and a summary table for review. Commit 02b1e1d contains the test pages, the scripts and the results as published, including the AI check. A different version of Chrome may give slightly different results.

How this differs from the original method

  • Automatic, not manual. GDS ran each tool by hand and judged whether the tool found the intended barrier on each page. The retest counts any finding that is not on the baseline page. It can therefore count a finding about something else on the page as a success.
  • Different versions and settings. The original results were recorded between 2016 and 2018 with the versions of the tools available then. GDS ran axe with the tags wcag2a, wcag2aa, section508, best-practice and experimental (see tools-info.md). The retest uses the WCAG tags up to 2.2 and best-practice, but not section508 or experimental. The retest runs HTML_CodeSniffer through pa11y. Its results are compared with the original HTML_CodeSniffer column.
  • Single pages only. GDS also used one large page with nearly all the tests. The retest only uses the single test pages.

Changes made after the first run

After the first retest, some added test pages caused findings that had nothing to do with the intended barrier. These pages were corrected and the retest was run again. Only added test pages were changed.

  • Links on seven pages (2.4.1, 2.4.5, 2.4.8, 2.4.11, 3.2.3, 3.2.4 and 3.2.6) were too close together and failed the target size rule. They were given space.
  • Headings in the added test cases were changed from h4 to h2, because the order of headings failed on its own.
  • The chat widget in the 2.4.12 test case had low text contrast. Its background colour was changed. axe still marks the contrast as needing review, probably because the widget overlaps other content, so this test case is “user to check” for axe.

One rule of the script was also changed after the first run. At first, pa11y notices counted as “user to check”. This put about 80% of the test cases in that group, because HTML_CodeSniffer gives generic notices on almost every page. Notices were then excluded, as described above. The raw findings still include them.

These changes are in the process log. They make the results fairer to the tools, but because they were made after seeing the results, they are a possible source of bias.

How the AI check was run

Preliminary. The AI check is an early experiment, and AIL does not yet trust the method. The model is given screenshots, but most of its findings rest on the HTML, the accessibility tree and values the evidence script measured, not on how the page looks: 61 of 314 findings refer to an image. Barriers that can only be seen, and markup errors that do not show on screen, may be judged wrongly. Treat the AI results as indications, not as measurements. Read the limitations.

The retest showed which test cases neither axe-core nor pa11y finds. AIL asked whether it is possible to describe how to test for these barriers so precisely that an AI can do it. The result is 35 test procedures in ai-checks.json, adapted from the manual checklist in sa11y, an internal tool that is not public. Every test case that the two tools do not find is covered by a procedure. The build fails if one is not.

What the model is given

The model cannot use the page itself. A script opens each page many times and records what happens: the HTML, the accessibility tree, computed styles, screenshots (also in grayscale, at 320 pixels wide, with doubled text, with WCAG text spacing and in both orientations), every Tab stop with a picture of it with and without focus, what changes on Enter, Space, click, Escape, hover, paste and pointer use, what happens when a form is sent empty, and what changes on its own in the first 3 seconds. Links and forms that would leave the page are recorded instead of followed. The full list is on the procedures page.

The model is given all the procedures and the evidence, and reports each procedure that fails or that it cannot judge, with the element, the evidence it relies on and the reason.

Keeping the answer from the model

The test pages often name their barrier. Before the evidence is collected:

  • The page title and first heading of each test page are replaced with “Test page”. On the example pages they are kept, because they are part of what is tested, unless they name the audit.
  • Class names and ids are replaced with neutral names such as c1 and id1. Many of them named the barrier, for example no-paste.
  • Comments and the content of scripts are removed. The model sees which events have listeners, not the code.
  • File names of pages and media are replaced, and URLs are removed from the accessibility tree. The model is not told the name of the test case.

This does not hide everything. On 34 test pages the text of the page itself describes the barrier, for example “This link opens in a new window without warning”, because GDS wrote the test pages for people. The results are therefore given both with and without these pages.

From findings to results

  1. Any failure gives “issue found”. Otherwise, any procedure the model cannot judge gives “user to check”. Otherwise the result is “not found”. This is the same as for axe-core and pa11y.
  2. A failure from a procedure written for that test case is not enough on its own: the reason could be about something else on the page. A second pass with the same model read the test case, its example and every failure, and judged whether a failure describes the intended barrier (111 yes, 4 partly, 4 no). The main score only counts “yes”, so the AI check is held to the same standard GDS used in the original audit. The judgements are in results/2026-10-01/ai-review.json. The score that counts any failure is also given.
  3. The 23 control pages have no known barrier: 21 pages built to pass the procedures, and the two baseline pages. Any failure on them is a false positive.

Changes made after the first runs

The procedures were first run on a few test cases and the control pages. This found errors in the evidence script and in the control pages, which were corrected before the full run:

  • Links and forms took the browser to another page during the tests, so some evidence was lost. They are now recorded and not followed.
  • Caption files were blocked on local files, so the model was told videos had empty captions.
  • With several pages open at once, pages in the background did not show focus or could not take screenshots. Each page is now checked in its own browser.
  • The evidence listed the event listeners of the script itself, and a listener from the shared page script that only one test case needs.
  • Escape was pressed after five Tab presses, so focus had already moved. It is now pressed straight after opening.
  • Three control pages had real barriers the model found: an alt text that did not match the image, a tooltip that could not be hidden, and lines of text longer than AAA allows. They were corrected.

Repeating the AI check

With access to Claude on Amazon Bedrock (AWS_REGION and the model in ANTHROPIC_DEFAULT_OPUS_MODEL):

npm run build
npm run ai-check -- --force

The script writes the findings to results/<date>/ai.json, a summary for review to results/<date>/ai-summary.md, and the results to retest.json. Each answer is cached in results/<date>/ai-cache/, so running it again without changes makes no requests. A full run took about 70 minutes and used about 2.4 million input tokens, 3.1 million cached input tokens (the procedures, sent with every request) and 0.12 million output tokens. The model does not give the same answer every time, so a new run will give slightly different results.

Limitations

  • The retest results are proposals from the script. Not all of them have been checked by hand to confirm the tool found the intended barrier.
  • The added test cases have not been reviewed by an independent accessibility expert. Some may not fail the criterion as clearly as intended, or may fail other criteria too.
  • The same AI session wrote both the test pages and the script that checks them, which may cause systematic errors in both.
  • Many of the added criteria (for example 3.1.3 Unusual Words or 2.2.3 No Timing) cannot be checked automatically at all. A “not found” for these is expected and says little about a tool’s quality.
  • The original results were recorded by people and may contain errors that have not been corrected here.
  • The same AI session wrote the added test pages, the AI test procedures, the evidence script, the control pages and the checker, and the AI check uses a model from the same family. The procedures were written knowing which test cases they should find. The AI check is not an independent measurement of what AI can do on real websites.
  • The test pages are small and each has one intended barrier. Real pages are larger and have many barriers, and the evidence for them would not fit in one request.
  • The AI check is preliminary. The model is given screenshots, but only 61 of its 314 findings refer to one. The others rest on the HTML, the accessibility tree and values the evidence script measured, such as line height, characters per line and border contrast. The model judges these values, not how the page looks. The images are also sent after all the text, and screenshots are cut off at 1600 pixels high. Barriers that can only be seen, and markup errors that do not show on screen, may therefore be judged wrongly.
  • The findings of the AI check have not all been checked by hand. Each has a reason and the evidence it relies on in results/2026-10-01/ai-summary.md, so they can be.
