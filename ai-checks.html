Accessibility tool audit

This is an independent copy of the accessibility tool audit by the Government Digital Service (GDS), maintained by A11y Intuition Lab (AIL). The GDS text has been adapted to say “GDS” where it said “we”. The retest and the added test cases were made by AIL in this copy and were not carried out, reviewed or endorsed by GDS. How AIL made this copy, including the use of AI.

AI test procedures for what axe and pa11y miss Not by GDS Preliminary

Preliminary. The AI check is an early experiment, and AIL does not yet trust the method. The model is given screenshots, but most of its findings rest on the HTML, the accessibility tree and values the evidence script measured, not on how the page looks: 61 of 314 findings refer to an image. Barriers that can only be seen, and markup errors that do not show on screen, may be judged wrongly. Treat the AI results as indications, not as measurements. Read the limitations.

These are the test procedures A11y Intuition Lab (AIL) wrote for the barriers that axe-core and pa11y do not find in the retest. Each procedure is written so that an AI model can follow it, and is adapted from a test in the manual checklist of sa11y, an internal tool that is not public. The procedures here are complete on their own and do not need sa11y. The procedures are in ai-checks.json. How they were run and what they found is described on the method page.

Each procedure has one of three levels:

  • AI: the model can judge from the page as it is: its HTML, accessibility tree, styles and a screenshot.
  • AI with harness: a script must act on the page first, for example press Tab, zoom or hover, and the model judges the result.
  • Person: the model cannot judge it, for example whether captions match the speech. It can at most flag that a person must check.

What the model is given

The script scripts/ai-evidence.mjs collects this evidence for each page. The model is not given the name of the test case, the file name or the URL.

dom
The HTML of the page after load. Comments and script contents are removed. Class names are replaced by neutral names (c1, c2, ...) because the test pages name the barrier in their classes. On test pages the title and first heading are replaced by 'Test page' because they name the test case.
source
The HTML file as written, before the browser repairs it, with the same changes as for dom.
axtree
The accessibility tree from Chrome: role, name, description, value and state of each node.
styles
Computed styles for visible text, links, form fields and buttons: font size, line height, style, transform, alignment, line length in characters, colours, borders, underline and the contrast ratio against the background.
listeners
Which event types (click, keydown, pointerdown, paste, devicemotion and so on) are attached to which elements. The handler code is not included.
media
For each audio, video, iframe and object element: source file name, duration, controls, autoplay, whether it is playing after load, and text tracks with their kind, language and cue text.
screenshot
A screenshot of the page at 1280 by 800 CSS pixels.
grayscale
The same screenshot in grayscale.
tab-sequence
The page is reset, then Tab is pressed up to 40 times. For each stop: the focused element, its position, its outline and box shadow, whether another element covers it, and a cropped screenshot of it with and without focus. Repeats are reported, which shows a keyboard trap.
activation
Each button, link to '#' or 'javascript:', and element with a click handler is activated with Enter and then Space from the keyboard. For each: what changed in the page, where focus is, and the next 5 Tab stops. If the page changed after Enter, it is loaded again, the element is activated with Enter, and Escape is pressed straight away: what changed and where focus is then (escapeAfterEnter).
keys
Each letter from a to z is pressed with focus on the page body. Any change to the page is recorded.
pointer
Each button and element with a pointer handler gets a pointer down without a pointer up, then a full click. Changes after each are recorded. Elements with a 'touchstart', 'devicemotion', 'dragstart' or pointer move handler are listed.
paste
Text is pasted into each text and password field. Whether the paste was blocked is recorded.
hover-focus
Each element is hovered and focused in turn. Content that appears is recorded, then Escape is pressed and the pointer is moved onto the new content. Whether the content stays is recorded.
submit-empty
Each form is submitted empty. The changes to the page, any live regions and where focus ends up are recorded.
timeline
Every change to the page from load until the end of all actions, with the time and the action that was last performed. This shows content that changes, disappears or updates on its own.
zoom-320
A screenshot at 320 CSS pixels wide, and whether the page scrolls horizontally.
text-200
A screenshot after every font size is doubled (similar to text-only zoom), and a list of elements whose text is clipped or overlaps other text.
text-spacing
A screenshot after the WCAG 1.4.12 text spacing style sheet is applied, and a list of elements whose text is clipped.
orientation
Screenshots in a portrait (800 by 1280) and a landscape (1280 by 800) viewport.
multi-page
When a test case has more than one page, the evidence for each page is given in turn. The navigation, header, footer and help links of each page are compared.

Everything can be done with the keyboard alone

About the procedure: Everything can be done with the keyboard alone
WCAG2.1.1, 2.1.2, 2.1.3, 4.1.2
LevelAI with harness
Evidencedom, listeners, tab-sequence, activation

Compare the interactive things on the page (links, buttons, controls, elements with click handlers, expandable sections, menus, drawing areas) with the Tab stops. Every interactive thing must be reachable with Tab and work with Enter or Space as expected for its role. Use the activation results to see whether Enter and Space do what a click does. A Tab sequence that repeats the same element and never reaches the end of the page, without a way out, is a keyboard trap. Elements that receive focus but do nothing (tabindex=0 on plain text or images) are a failure.

Pass

  • All links, buttons and form fields get focus.
  • Enter and Space activate buttons, and Enter activates links.
  • Focus can always leave a component with Tab or Escape.
  • Only interactive elements are in the Tab order.

Fail

  • A clickable element (a div with a click handler, a 'button' made from a link without href) cannot be reached with Tab.
  • Sub-items of a menu or the content of an expandable section can only be reached by hovering or clicking.
  • A link with role=button does not react to Space.
  • Focus is stuck on one element or a few elements.
  • A non-interactive element is in the Tab order because of tabindex=0.
  • A function such as signing can only be done by drawing with a pointer, with no keyboard alternative (2.1.3).

Limits: The harness presses each key once. Components that need arrow keys or typing are judged from the role and handlers only.

Test cases

  • Keyboard focus assigned to a non focusable element using tabindex=0
  • Concertina items don't get keyboard focus
  • Dropdown navigation - only the top level items receive focus
  • Signature can only be drawn with a pointer

Focus is always visible and clear

About the procedure: Focus is always visible and clear
WCAG2.4.7, 2.4.13, 1.4.11
LevelAI with harness
Evidencetab-sequence, styles

For each Tab stop, compare the cropped screenshot with and without focus. There must be a clearly visible change. For 1.4.11 the focus indicator must have a contrast of at least 3:1 against the colours next to it. For 2.4.13 (AAA) it must be at least as large as a 2 CSS pixel solid outline around the element and have at least 3:1 contrast between the focused and unfocused states.

Pass

  • The focus indicator is visible on every stop and has at least 3:1 contrast against the background.

Fail

  • outline: none with no other visible change, so it is impossible to see where focus is.
  • Focus is only shown as a faint change of background or a light ring on white.
  • The focus indicator is a 1 pixel dotted line with low contrast (2.4.13).

Limits: The model judges contrast from the screenshots and computed colours. Borderline values near 3:1 should be cannot-tell.

Test cases

  • Focus not visible
  • Keyboard focus is not indicated visually
  • Focus indicator is too thin and has low contrast

The focused element is not hidden by other content

About the procedure: The focused element is not hidden by other content
WCAG2.4.11, 2.4.12
LevelAI with harness
Evidencetab-sequence

For each Tab stop, check whether another element covers the focused element. 2.4.11 (AA) fails when the focused element is entirely hidden by content the author created, such as a sticky header, footer, cookie banner or chat widget. 2.4.12 (AAA) fails when any part of it is hidden.

Pass

  • No part of the focused element is covered by other content.

Fail

  • Links behind a sticky footer get focus but are completely covered (2.4.11).
  • Half of a focused link is covered by a chat widget (2.4.12).

Limits: Covering is measured at the centre and corners of the element at 1280 by 800.

Test cases

  • Focused link is hidden behind a sticky footer
  • Focused link is partly hidden by a chat widget

Focus order follows the meaning and is managed in dialogs

About the procedure: Focus order follows the meaning and is managed in dialogs
WCAG2.4.3, 2.1.2
LevelAI with harness
Evidencescreenshot, tab-sequence, activation

Compare the order of the Tab stops with the visual reading order in the screenshot. For each dialog, lightbox or overlay that opens on activation: focus must move into it, Tab must stay inside it while it is modal, it must have a close control that can be reached and used with the keyboard, Escape should close it, and focus should return to the control that opened it.

Pass

  • Tab order follows the visual reading order.
  • Focus moves into a dialog when it opens and stays there until it is closed.
  • The dialog can be closed with the keyboard, and focus returns to the opener.

Fail

  • Focus jumps between parts of the page in an order that does not match the layout.
  • After a dialog opens, focus stays behind it or the next Tab stops are on the page under it.
  • Tab leaves an open modal dialog and goes to the page behind it.
  • The close control of a dialog cannot be focused.
  • Escape does not close a dialog and there is no other keyboard way to close it.

Limits: Escape not closing a dialog is a failure only when it is the only way out or when the dialog behaves as modal. Report it as a fail under this check when other dialog behaviour is also wrong, otherwise as cannot-tell.

Test cases

  • Focus order in wrong order
  • Lightbox - close button doesn't receive focus
  • Lightbox - ESC key doesn't close the lightbox
  • Lightbox - focus is not moved immediately to lightbox
  • Lightbox - focus is not retained within the lightbox

Repeated blocks can be skipped

About the procedure: Repeated blocks can be skipped
WCAG2.4.1, 1.3.6
LevelAI with harness
Evidencedom, axtree, tab-sequence

If the page has a block of navigation or other content that would repeat on every page, there must be a way to skip it: a skip link that is the first Tab stop and moves focus, or landmarks (header, nav, main) and headings. For 1.3.6 (AAA), the purpose of regions such as navigation, search and main content must be programmatically determined, for example with landmarks.

Pass

  • The first Tab stop is a skip link that moves focus past the navigation.
  • The page uses landmarks for navigation and main content.

Fail

  • The page has a long navigation menu and no skip link, landmarks or headings to jump past it.
  • Navigation, search and main content are plain divs with nothing to identify them (1.3.6).

Limits: A single test page does not repeat, so the model judges whether a block looks like repeated site navigation.

Test cases

  • No way to skip repeated navigation
  • Purpose of regions cannot be programmatically determined

Single-key shortcuts can be turned off and accesskey is not used

About the procedure: Single-key shortcuts can be turned off and accesskey is not used
WCAG2.1.4
LevelAI with harness
Evidencedom, listeners, keys

Look at what happened when each letter was pressed. If a single letter, number or punctuation key triggers an action without a modifier key, there must be a way to turn it off or change it, or it must work only when a specific component has focus. Also report the accesskey attribute, which creates shortcuts that can conflict with assistive technology (best practice).

Pass

  • Letters do nothing unless a field or component has focus.
  • Shortcuts need a modifier key, or there is a setting to turn them off.

Fail

  • Pressing a letter on the page performs an action, and there is no way to turn this off.
  • An element has an accesskey attribute.

Limits: Only a to z are pressed.

Test cases

  • Single character keyboard shortcut cannot be turned off or remapped
  • Accesskey attribute used

Focus and input do not change context unexpectedly

About the procedure: Focus and input do not change context unexpectedly
WCAG3.2.1, 3.2.2, 3.2.5
LevelAI with harness
Evidencetab-sequence, activation, timeline

Check whether moving focus to an element opened a window, moved focus elsewhere, submitted a form or changed the page in a major way (3.2.1). Check whether changing a field value did so without warning (3.2.2).

Pass

  • Moving focus never causes anything to happen on its own.

Fail

  • Focusing a field opens a new window or pop-up.
  • Choosing an option in a select changes the page language or navigates without a button.

Limits: New windows are detected when the page calls window.open.

Test cases

  • Focusing a field opens a new window

Content shown on hover or focus can be dismissed, hovered and stays

About the procedure: Content shown on hover or focus can be dismissed, hovered and stays
WCAG1.4.13
LevelAI with harness
Evidencedom, hover-focus

For each piece of content that appeared on hover or focus: it must be dismissible with Escape without moving pointer or focus (unless it does not cover other content), the pointer must be able to move onto it without it disappearing, and it must stay until the user dismisses it or moves away.

Pass

  • Tooltips stay while hovered, can be hovered themselves, and close with Escape.

Fail

  • A tooltip that covers other content cannot be closed with Escape.
  • A tooltip disappears when the pointer moves onto it.

Limits: The native title attribute tooltip is drawn by the browser and is not judged here.

Test cases

  • Tooltip cannot be dismissed without moving the pointer or focus
  • Tooltip disappears when the pointer is moved over it

Pointer actions have simple alternatives and can be cancelled

About the procedure: Pointer actions have simple alternatives and can be cancelled
WCAG2.5.1, 2.5.2, 2.5.4, 2.5.6, 2.5.7
LevelAI with harness
Evidencedom, listeners, pointer, screenshot

Look for functions that need a path-based gesture (swipe), dragging, device motion (shake, tilt), or that trigger on pointer down. Each needs a single-pointer alternative without dragging, such as buttons (2.5.1, 2.5.7), or a user interface alternative and a way to turn motion off (2.5.4). An action that completes on pointer down without a way to abort or undo fails 2.5.2. Content must not ignore a mouse or other input method when a touch screen is present (2.5.6, AAA).

Pass

  • Every gesture, drag or motion function also has visible buttons or another simple control.
  • Actions happen on click (pointer up), not pointer down.

Fail

  • A carousel only changes with a swipe and has no next and previous buttons.
  • A list can only be reordered by dragging.
  • A function can only be used by shaking the device.
  • An action happens on pointer down (mousedown) and cannot be undone.
  • A button ignores mouse clicks when the device has a touch screen.

Limits: The harness does not perform real gestures. The model judges from the handlers, the controls present and the pointer-down result.

Test cases

  • Carousel can only be changed with a swipe gesture
  • Action is triggered on pointer down
  • Function can only be operated by shaking the device
  • List can only be reordered by dragging
  • Mouse input is ignored on devices with a touch screen

The accessible name contains the visible label

About the procedure: The accessible name contains the visible label
WCAG2.5.3
LevelAI
Evidenceaxtree, screenshot

For each control with visible text, compare the visible text with the accessible name in the accessibility tree. The name must contain the visible text, preferably at the start.

Pass

  • A button that shows 'Send' has an accessible name that contains 'Send'.

Fail

  • A button shows 'Send' but its accessible name is 'Submit message'.

Test cases

  • Accessible name does not contain the visible label

Link text says where the link goes

About the procedure: Link text says where the link goes
WCAG2.4.4, 2.4.9
LevelAI
Evidencedom, axtree

For each link, read its accessible name, its surrounding sentence or paragraph, and its href. Its purpose must be clear from the name together with the context (2.4.4), and for 2.4.9 (AAA) from the name alone. Links with the same name must go to the same place. Adjacent links to the same destination (an image and a text link) should be combined. A title attribute that only repeats the link text adds nothing. A link whose text is only punctuation is a failure. An image that is the only content of a link must have alt text that says where the link goes.

Pass

  • Each link name describes its destination, such as 'Read more about polar bears'.

Fail

  • Link text such as 'Read more', 'Click here' or 'page' that does not make sense out of context.
  • The link is only a full stop.
  • Two links with the same text go to different pages.
  • An image link and a text link next to each other go to the same place.
  • A link's title is the same as its text.
  • A link around an image has no text alternative, or its alt repeats the text next to it.

Test cases

  • Link text does not make sense out of context
  • Non-specific link text
  • Links with the same text go to different pages
  • Adjacent links going to the same destination
  • Link contains only a full stop
  • Link text with identical title
  • Link to an image, no text alternative

Links are real links and say what they open

About the procedure: Links are real links and say what they open
WCAG2.4.4, 3.2.5, 4.1.2
LevelAI
Evidencedom, axtree

Check each link's href and target. A link with href='#' or 'javascript:' that does an action should be a button. A link that opens a new window (target=_blank) should say so. A link to a file (PDF, sound, video) should give the file type and size. Separate adjacent links with printable characters or list markup, not only spaces.

Pass

  • Links go to real pages or anchors. File links say 'PDF, 2 MB'. New windows are announced.

Fail

  • href='javascript:...' or href='#' used for an action.
  • target=_blank with no warning in the text or name.
  • A PDF link without format and size.
  • Several links next to each other with nothing between them except spaces.

Test cases

  • Link to javascript, invalid hypertext reference
  • Link to #, invalid hypertext reference
  • Link launches new window with no warning
  • Link to PDF does not include information on file format and file size
  • Links not separated by printable characters

Links can be told apart from text without colour

About the procedure: Links can be told apart from text without colour
WCAG1.4.1
LevelAI
Evidencestyles, screenshot, grayscale

For each link inside running text, look at the underline, font weight and colour. If colour is the only difference from the surrounding text, the colour contrast between link and text must be at least 3:1 and there must be another cue on hover and focus. A link that looks just like the surrounding text fails.

Pass

  • Links in text are underlined.

Fail

  • A link in a paragraph has no underline and differs from the text only by a similar colour, or not at all.

Test cases

  • Link not clearly identifiable and distinguishable from surrounding text

Colour is not the only way to convey information

About the procedure: Colour is not the only way to convey information
WCAG1.4.1, 1.3.3
LevelAI
Evidencescreenshot, grayscale, dom

Compare the colour and grayscale screenshots. Any information that is lost in grayscale (which items are safe, which fields have errors, which is selected) fails. Also check instructions that rely only on shape, size, location or sound, such as 'the button on the right' (1.3.3).

Pass

  • Information is also given in text, an icon or a pattern.
  • Instructions name the thing, not only where it is.

Fail

  • Edible and poisonous items are only shown in green and red.
  • Text refers to content only by where it is on the page, such as 'the artist on the right'.

Test cases

  • Colour alone is used to convey content
  • Content identified by location

Controls and graphics have at least 3:1 contrast

About the procedure: Controls and graphics have at least 3:1 contrast
WCAG1.4.11
LevelAI
Evidencestyles, screenshot

For each form field, button without a background fill, and icon that is needed to understand or use a control, check the contrast of the boundary or icon against the adjacent colour. It must be at least 3:1. Use the computed colours where given.

Pass

  • Field borders and icon buttons have at least 3:1 contrast against the background.

Fail

  • A text field has a light grey border on white (below 3:1).
  • An icon-only button uses a pale icon on white.

Limits: Contrast of gradients and images cannot be computed. Values close to 3:1 should be cannot-tell.

Test cases

  • Form field border does not have a contrast ratio of at least 3:1
  • Icon-only button does not have a contrast ratio of at least 3:1

Blocks of text are easy to read

About the procedure: Blocks of text are easy to read
WCAG1.4.8
LevelAI
Evidencestyles, screenshot

For each block of text (a paragraph or more), check: line height at least 1.5, lines not longer than 80 characters, not justified, no long passages in italics or all capitals (text-transform or typed capitals), and body text not very small (below about 12 CSS pixels). These are 1.4.8 (AAA) and common readability advice.

Pass

  • Text blocks have line height 1.5 or more, lines under 80 characters, left aligned, regular style and readable size.

Fail

  • A paragraph has line height 1 or less.
  • Lines run across the full page at well over 80 characters.
  • A paragraph is justified.
  • A long passage is in italics or capitals.
  • Body text is set at a very small size.

Limits: Short labels and headings are not judged.

Test cases

  • Inadequate line height used
  • All caps text found
  • Italics used on long sections of text
  • Long lines of text
  • Very small text found
  • Justified text found

Content works with larger text, more spacing and narrow screens

About the procedure: Content works with larger text, more spacing and narrow screens
WCAG1.4.4, 1.4.10, 1.4.12
LevelAI with harness
Evidencescreenshot, zoom-320, text-200, text-spacing

Compare the normal screenshot with the screenshots after text is doubled, after text spacing is applied, and at 320 pixels. Content or functions must not be lost: text must not be clipped, overlap other text, or be cut off by a box that does not grow. At 320 pixels, the page must not need horizontal scrolling for text.

Pass

  • All text is still readable and nothing is cut off in any of the screenshots.

Fail

  • Text overlaps or becomes unreadable when the text size is doubled.
  • A box with a fixed height cuts off its text when the text is larger.
  • Text is clipped when the line, word or letter spacing is increased.

Limits: Doubling every font size is close to, but not the same as, text-only zoom in a browser.

Test cases

  • Content is not readable and functional when text is increased
  • Page zoom - boxes that don't expand with the text
  • Content is clipped when text spacing is increased

Content works in both portrait and landscape

About the procedure: Content works in both portrait and landscape
WCAG1.3.4
LevelAI with harness
Evidenceorientation

Compare the portrait and landscape screenshots. Content must not be locked to one orientation, for example by rotating it or hiding it in the other, unless the orientation is essential.

Pass

  • The content can be read in both orientations.

Fail

  • Content is rotated or hidden in landscape so it can only be read in portrait.

Test cases

  • Content is locked to one display orientation

Text is real text, not an image

About the procedure: Text is real text, not an image
WCAG1.4.5, 1.4.9
LevelAI
Evidencedom, screenshot

Look at each image in the screenshot. If it mainly shows text that could be real text with styling, it fails 1.4.5 (AA). For 1.4.9 (AAA), only logos and cases where the exact look is essential are allowed, so a quotation, heading or banner as an image fails.

Pass

  • Text is HTML text styled with CSS. Images of text are only logos.

Fail

  • A heading or notice is an image of text.
  • A quotation is shown as an image.

Test cases

  • Image of text used instead of text
  • Image of text used for a quotation

Images have a text alternative that serves the same purpose

About the procedure: Images have a text alternative that serves the same purpose
WCAG1.1.1
LevelAI
Evidencedom, axtree, screenshot, styles

For each image (img, input type=image, role=img, background images that contain information, CSS generated content, svg), look at what it shows in the screenshot and compare with its text alternative. Informative images need an alternative that gives the same information. Decorative images need empty alt. An image button needs alt that says what the button does. Alt must not be a file name, and must not be contradicted by the title. Information given only in a CSS background image or CSS generated content is not available to screen readers.

Pass

  • Each image's alt gives the information in the image, or is empty if the image is decoration.

Fail

  • alt is a file name such as 'IMG_1234.jpg'.
  • alt does not describe the image or gives only part of the information.
  • An informative image has alt=''.
  • alt and title of the same image say different things.
  • An image button has alt such as 'button' or 'submit' that does not say what it does.
  • Information is shown only in a CSS background image or inserted with CSS content.
  • A spacer image is used for layout.

Test cases

  • Image has alt and title that are different
  • Background image that conveys information does not have a text alternative
  • Image that conveys information has an empty alt attribute
  • Image that conveys information has inappropriate alt text
  • Image alt attribute contains image file name
  • Image with partial text alternative
  • Uninformative alt attribute value on image button
  • Non-decorative content inserted using CSS
  • Spacer image found

Content meant for screen readers is not hidden from them

About the procedure: Content meant for screen readers is not hidden from them
WCAG1.3.1, 1.3.2, 2.4.4
LevelAI
Evidencedom, axtree

Compare the DOM with the accessibility tree. Text that is hidden with display:none or visibility:hidden is removed for screen reader users too. If that text is needed (such as the end of a link name like 'about rugby'), it should be hidden visually with a technique that keeps it in the accessibility tree.

Pass

  • Visually hidden helper text is still in the accessibility tree.

Fail

  • Part of a link name is hidden with display:none or visibility:hidden, so the link is only 'Read more'.

Test cases

  • visibility:hidden used to visually hide content when it should be available to screenreader
  • display:none used to visually hide content when it should be available to screenreader

Headings, lists and groups are marked up

About the procedure: Headings, lists and groups are marked up
WCAG1.3.1, 2.4.6, 2.4.10
LevelAI
Evidencedom, axtree, screenshot

Compare how the page looks with its markup. Text that looks like a heading must be a heading element. Items that look like a list (bullets typed as characters, one per line) must be list markup. Long content should be divided into sections with headings, lists and paragraphs. Empty paragraphs used for spacing and other leftover markup are best-practice failures.

Pass

  • Visual headings are h1 to h6, visual lists are ul or ol, and long content is split into sections.

Fail

  • A bold, large div is used as a heading.
  • A list is typed with '*' and line breaks.
  • A long page of text has no headings or other structure.
  • Empty p elements are used to add space.

Test cases

  • Text formatting used instead of an actual heading
  • List not marked up as a list
  • Content is not organised into well-defined groups or chunks, using headings, lists, and other visual mechanisms
  • Empty paragraph

Data tables have a clear and simple structure

About the procedure: Data tables have a clear and simple structure
WCAG1.3.1
LevelAI
Evidencedom, screenshot

For each table, check: data tables have a caption or another way to name the table; headers are th and data are td (a table made only of th is wrong); tables are not nested inside other tables; empty data cells are avoided or explained; and layout is not done with tables.

Pass

  • The table has a caption, header cells for rows or columns, data cells for data, and no nested tables.

Fail

  • A data table has no caption or name.
  • Every cell is a th.
  • A table contains another table.
  • Many cells are empty with no explanation.

Test cases

  • Table nested within table
  • Table that only has TH elements in it
  • Table is missing a caption
  • Table with some empty cells

The language and direction of text are marked up

About the procedure: The language and direction of text are marked up
WCAG3.1.1, 3.1.2, 1.3.2
LevelAI
Evidencedom, screenshot

Read the text and identify the language of the page and of every phrase in another language. The html element must have the correct lang. Each phrase in another language needs a lang attribute with the correct code. Text in a right-to-left language (Arabic, Hebrew) needs dir='rtl', and left-to-right text must not be set to rtl.

Pass

  • lang on html matches the page, phrases in other languages have the correct lang, and direction is correct.

Fail

  • A French phrase in English text has no lang attribute.
  • A phrase has lang set to the wrong language.
  • Arabic text has no dir='rtl'.
  • English text is marked dir='rtl'.

Limits: Proper names and words that have become part of the surrounding language do not need lang.

Test cases

  • Text language changed without required change in direction
  • lang attribute not used to identify change of language
  • Text language is in the wrong direction
  • lang attribute used to identify change of language, but with wrong language

Text is plain, and unusual words, abbreviations and pronunciation are explained

About the procedure: Text is plain, and unusual words, abbreviations and pronunciation are explained
WCAG3.1.3, 3.1.4, 3.1.5, 3.1.6
LevelAI
Evidencedom

Read the text. Text that needs more than lower secondary education to understand should be simplified or have a simpler version (3.1.5). Jargon and idioms must be explained (3.1.3). The first use of an abbreviation must be expanded or marked up (3.1.4, and best practice for the first instance). Where the meaning of a word depends on how it is pronounced (such as 'record' as noun or verb), the pronunciation must be given (3.1.6).

Pass

  • Text is short and plain, and abbreviations, idioms and ambiguous words are explained.

Fail

  • Long legal or technical sentences with no plain summary.
  • An abbreviation is used without being expanded.
  • Idioms or jargon such as 'kicked into the long grass' are not explained.
  • Words that are spelled the same but pronounced differently make the meaning unclear, and no pronunciation is given.

Test cases

  • Plain language is not used
  • First instance of abbreviation not expanded
  • Idioms and jargon are not explained
  • Meaning depends on pronunciation that is not given

Frames and embedded objects are named and work for everyone

About the procedure: Frames and embedded objects are named and work for everyone
WCAG4.1.2, 2.1.1
LevelAI
Evidencedom, axtree, media

Each iframe needs a title that describes its content or purpose. Compare the title with the content of the frame. Embedded objects (object, embed) should have a text alternative and use wmode=window for plugin content.

Pass

  • The iframe title describes what is in the frame.

Fail

  • An iframe title such as 'iframe' or a title that does not match the content.
  • A plugin object without wmode set to window.

Limits: The model sees the frame source file name and its title, and the content if it can be read.

Test cases

  • iframe title attribute does not describe the content or purpose of the iframe
  • Object not embedded accessibly - wmode parameter not set to window

Status messages and errors are announced and helpful

About the procedure: Status messages and errors are announced and helpful
WCAG4.1.3, 3.3.1, 3.3.3
LevelAI with harness
Evidenceactivation, submit-empty, timeline, dom

For each message that appeared after an action (added to basket, saved, errors), check that it is in a live region (role=status, role=alert or aria-live) or that focus moved to it. Messages that disappear after a short time must stay long enough to read, or be available again.

Pass

  • Messages appear in a live region and stay until dismissed.

Fail

  • A message such as 'Added to basket' appears in a plain element with no live region.
  • An alert is shown for a few seconds and then removed.

Limits: The model cannot hear a screen reader. It judges from the markup of the message.

Test cases

  • Status message is not announced to assistive technologies
  • Alert shows for a short time

Forms identify input purpose, help, and do not block or repeat input

About the procedure: Forms identify input purpose, help, and do not block or repeat input
WCAG1.3.5, 3.3.5, 3.3.7, 3.3.8
LevelAI with harness
Evidencedom, paste

Fields that ask for information about the user (name, email, phone, address) need the matching autocomplete value (1.3.5). Information the user already gave in the same process must be filled in or selectable, not typed again (3.3.7). Pasting into password and code fields must not be blocked (3.3.8). Complex fields need help or instructions (3.3.5, AAA).

Pass

  • Personal fields have autocomplete, earlier answers are reused, paste works, and complex fields have hints.

Fail

  • Name and email fields have no autocomplete attribute.
  • A billing address must be typed again although the delivery address was given in step 1, with no 'same as' option.
  • Paste is blocked in a password field.
  • A field asks for a reference number with no hint where to find it.

Test cases

  • Input purpose is not identified
  • Information entered earlier must be entered again
  • Pasting into the password field is blocked
  • No help is available for a complex field

Important submissions can be checked, confirmed or reversed

About the procedure: Important submissions can be checked, confirmed or reversed
WCAG3.3.4, 3.3.6
LevelAI with harness
Evidencedom, activation

For forms that make payments, legal commitments or delete data, there must be a way to check and correct the information, confirm, or undo (3.3.4 for legal and financial, 3.3.6 AAA for all submissions). Look at what happens on activation: is there a confirmation step?

Pass

  • A summary page or a confirmation dialog comes before the action, or the action can be undone.

Fail

  • Pressing 'Pay' or 'Delete all' acts immediately, with no confirmation or undo.

Limits: The harness cannot follow the real flow after a submission. The model judges from what the page shows.

Test cases

  • Payment is taken without a chance to check or cancel
  • Submitting a form cannot be checked, confirmed or reversed

Signing in does not need a cognitive test

About the procedure: Signing in does not need a cognitive test
WCAG3.3.8, 3.3.9
LevelAI
Evidencedom, screenshot

If signing in needs the user to remember, transcribe, solve or recognise something, there must be an alternative. For 3.3.8 (AA), recognising objects or personal content is allowed. For 3.3.9 (AAA) it is not.

Pass

  • Sign in works with a password manager, paste, or a link sent by email.

Fail

  • Sign in requires selecting every picture of an object (3.3.9).

Test cases

  • Sign in requires recognising objects in pictures

Time limits and interruptions can be controlled

About the procedure: Time limits and interruptions can be controlled
WCAG2.2.1, 2.2.3, 2.2.4, 2.2.5, 2.2.6
LevelAI with harness
Evidencedom, timeline

Look for time limits in the text and in the timeline (countdowns, content that is cleared or changes after a delay). For AAA, timing must not be part of an activity unless it is real-time (2.2.3); interruptions such as automatic updates must be possible to postpone or turn off (2.2.4); when a session expires, the user must be able to continue without losing data after signing in again (2.2.5); and users must be told about any inactivity timeout that can lose data (2.2.6).

Pass

  • There is no time limit, or the user can turn it off, extend it, or is warned and keeps their data.

Fail

  • A question must be answered within 60 seconds.
  • A message is announced every few seconds and cannot be turned off.
  • After the session expires, the user must start again from the beginning.
  • Typed text is cleared after inactivity without warning.

Limits: The harness watches the page for a few seconds only. Long time limits are judged from the text and handlers.

Test cases

  • Task has a time limit
  • Updates interrupt the user and cannot be postponed
  • Data is lost when the session expires
  • Users are not warned about an inactivity timeout

Moving, blinking and flashing content can be controlled

About the procedure: Moving, blinking and flashing content can be controlled
WCAG2.2.2, 2.3.1, 2.3.2, 2.3.3
LevelAI with harness
Evidencedom, media, timeline, activation

Look for animated images (gif), blinking or scrolling text, and content that flashes. Animation that starts automatically and lasts more than 5 seconds needs a pause control. Content that flashes more than three times in a second fails 2.3.2 (AAA). Motion animation started by interaction must respect reduced motion or be possible to turn off (2.3.3, AAA).

Pass

  • There is no automatic animation, or it can be paused. Animation stops when reduced motion is requested.

Fail

  • An animated gif loops with no way to stop it.
  • An element changes its appearance more than three times a second.
  • An element spins or slides on interaction even with reduced motion requested.

Limits: The model cannot measure flash rate or area from screenshots. It judges from the timeline and the code-free description of changes. A person must check flash thresholds.

Test cases

  • A distraction is present, an animated gif
  • Content flashes more than three times in one second
  • Flashing content doesn't have warning
  • Motion animation triggered by interaction cannot be turned off

Audio and video have the alternatives they need

About the procedure: Audio and video have the alternatives they need
WCAG1.2.1, 1.2.2, 1.2.3, 1.2.4, 1.2.6, 1.2.7, 1.2.8, 1.2.9, 1.4.2, 1.4.7
LevelPerson
Evidencedom, media, timeline

The model cannot hear audio or watch video. From the media evidence it can check: recorded audio needs a transcript nearby or linked (1.2.1); video needs captions (a captions track) and audio description or a text alternative (1.2.2, 1.2.3); live video needs live captions (1.2.4); for AAA, sign language (1.2.6), extended audio description (1.2.7), a full text alternative (1.2.8), and a text alternative for live audio (1.2.9). Audio that plays automatically for more than 3 seconds needs a way to pause or turn down (1.4.2). Links to audio or video files need a transcript nearby. Whether speech has loud background music (1.4.7) cannot be judged without listening.

Pass

  • Media has controls, a captions track and a transcript, and does not play automatically.

Fail

  • Audio or video with no transcript, captions track or text alternative.
  • A live stream with no captions.
  • Audio plays on load with no controls.
  • A link to an audio or video file with no transcript.

Limits: Report cannot-tell when media is present and the needed alternative depends on its content, such as whether a sign language version, extended description or quiet background is needed.

Test cases

  • Embedded video file is missing text alternative
  • Embedded audio file is missing text alternative
  • Live video stream has no captions
  • Video has no sign language interpretation
  • Video has no extended audio description
  • Live audio stream has no text alternative
  • Audio plays automatically with no way to stop it
  • Speech has loud background music
  • Links to a sound file, no transcript
  • Link to a multimedia file, no transcript

Navigation, help and functions are consistent across pages

About the procedure: Navigation, help and functions are consistent across pages
WCAG2.4.5, 2.4.8, 3.2.3, 3.2.4, 3.2.6
LevelAI with harness
Evidencemulti-page, dom, screenshot

When several pages are given, compare them: navigation links in the same order (3.2.3), the same function with the same label (3.2.4), and help (contact, chat, help link) in the same relative place (3.2.6). On any site page: there must be more than one way to find pages, such as search, a site map or links between pages (2.4.5), and for AAA the page must show where the user is in the site, such as breadcrumbs or a highlighted menu item (2.4.8).

Pass

  • Repeated parts are the same on every page. The site has search or a site map. The current section is shown.

Fail

  • The help link is in the header on one page and the footer on another.
  • The search button is 'Search' on one page and 'Go' on another.
  • The only way to find pages is the menu.
  • There are no breadcrumbs or other sign of where the user is.

Limits: 2.4.5 and 2.4.8 are about the whole site. The model judges from what the page itself offers.

Test cases

  • Help link is in a different place on each page
  • Pages can only be found in one way
  • No indication of where the user is in the site
  • The same function has different labels on different pages

Markup is valid and uses the right elements

About the procedure: Markup is valid and uses the right elements
WCAG1.3.1, 4.1.1
LevelAI
Evidencedom, source

Look for markup that produces the wrong structure: start and end tags that do not match, presentational markup such as inline colour styles that carry meaning, and pre elements used for something other than preformatted text or code (such as ASCII art without a text alternative). 4.1.1 Parsing was removed in WCAG 2.2, so mismatched tags are reported as best practice.

Pass

  • Elements are properly nested and closed, and preformatted text is code or has an alternative.

Fail

  • An element is opened with one tag and closed with another.
  • A pre element holds ASCII art with no text alternative.
  • Colour set with an inline style is the only cue for meaning.

Limits: The model sees the DOM after the browser has repaired the HTML, so it may not see mismatched tags. The original source is also given for this check.

Test cases

  • Start and close tags don't match
  • PRE element without CODE element inside it
  • Inline style adds colour
