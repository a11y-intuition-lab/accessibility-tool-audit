# Automated pre-step

> Status: AI-drafted, not human-reviewed

This is the automated pre-step, not a group. It runs on every page before any group (decision D-028). Run two independent rule engines (axe-core and HTML_CodeSniffer through pa11y) over the page and store their raw output. Its output (axe violations and incomplete results, HTMLCS errors, warnings and notices, each mapped to criteria) is passed to every group as context. It decides no criterion alone: a reported violation is a candidate failure, "incomplete" or a warning is a request for review, and a rule that did not fire is not evidence of a pass. It is the cheapest step. No success criterion has full automation in our triage, so the pre-step has no primary criteria. The criteria below are those where automation is partial.

## Setup

- Headless Chromium, viewport 1280 x 1024, device scale factor 1, light colour scheme, JavaScript on, no extensions, clean profile.
- axe-core, version pinned and recorded, all rule tags enabled: wcag2a, wcag2aa, wcag2aaa, wcag21a, wcag21aa, wcag22aa, best-practice, experimental.
- pa11y with the HTML_CodeSniffer runner, version pinned and recorded: main pass `WCAG2AAA` with warnings and notices included, supplementary pass `WCAG2AA` (D-024: the `WCAG2AAA` ruleset lacks some sniffs, such as the 2.2.1 meta refresh checks).
- Wait for the load event plus 2 seconds of network idle before running, so script-built content exists.
- AI capability needed: none for collection. A script does this step. An AI only reads the stored output in a group's judging step.

## Collect

Collect all of this before judging. Each item names the data type (`needs` key in the data file). A script or a cheap model can do it without judgement; store each artifact with a file name that the report can cite.

1. **dom** — Load the URL, wait as described, then run axe-core on the whole page. Store the complete result object: `violations`, `incomplete`, `passes`, `inapplicable`, with node selectors and the rule's tags.
2. **dom** — Run pa11y with the `WCAG2AAA` standard, warnings and notices on, `ignore` list empty. Store every issue with `type` (error, warning, notice), `code`, `selector`, `message`.
3. **dom** — Run pa11y again with the `WCAG2AA` standard, same settings. Store separately.
4. **dom** — If the page links to or embeds other pages needed to judge a rule (for example frames or a linked example page), run both tools on those too and store per URL.
5. **screenshot** — Save one full-page screenshot at 1280 px so a reviewer can find the nodes the tools name.
6. **dom** — Record tool versions, browser version, viewport, settings and a timestamp in one environment record.

## How the groups use the output

Map each stored tool result to criteria with the rule-to-criterion table in the data file (`automation.rules`), never by reading a message and guessing. The pre-step itself records no outcome; each group takes the mapped results for its criteria as context and gives the outcome in its own pass.

- A tool `violation` (axe) or `error` (HTMLCS) on a rule mapped to the criterion: a candidate `failed`. The group confirms it on the node (confidence high for axe rules that decide the whole condition, medium for rules that only detect one failure pattern).
- axe `incomplete`, or an HTMLCS `warning`: a request for review. The group named as primary for the criterion judges the node and the reason.
- HTMLCS `notice`: not evidence. It is a page-level reminder; use it only to know that the element type exists.
- A rule that ran and passed: evidence only for the exact condition the rule tests, never for the whole criterion; all our criteria are partial or none.
- A mapped rule with no applicable nodes (`inapplicable`): applies to that rule, not to the criterion.
- Deprecated and best-practice rules (for example 4.1.1 duplicate ids, landmark rules) are reported, but tagged so the report shows they are not current WCAG 2.2 requirements.

Notes for criteria where a rule needs care:

- 1.4.3 and 1.4.6 (contrast, see [visual](./recipes/visual.md)): axe `color-contrast` and `color-contrast-enhanced` settle text on solid backgrounds; text over images, gradients or overlaps returns `incomplete` and goes to the visual group. 1.4.6 is AAA; mention that GOV.UK 2017 did not enable AAA tags.
- 2.5.8 (target size, see [pointer-motion](./recipes/pointer-motion.md)): axe `target-size` checks the 24 CSS px minimum and spacing; exceptions (inline, equivalent control, user-agent control, essential) need the pointer-motion group.
- 4.1.1 (parsing, see [code-and-tree](./recipes/code-and-tree.md)): removed in WCAG 2.2. axe `duplicate-id` and `duplicate-id-active` and HTMLCS F77 catch duplicate ids only.

### Possible future extensions (not part of the pre-step now)

The data file lists specialised tools outside the project's toolset under `otherTools`: an HTML validator (Nu Html Checker) that could decide 4.1.1 fully, and a flash analyser (for example PEAT) for 2.3.1 and 2.3.2. They were not tested in phase 1, are not counted in the automation levels, and could be added to the pre-step later.

## Report

Write one finding per criterion and location. Use exactly these fields.

| Field | Content |
|---|---|
| `criterion` | Success criterion id, for example `1.4.3` |
| `outcome` | `failed`, `passed`, `inapplicable` or `cantTell` |
| `location` | Page URL plus CSS selector of the element (or `page` for page-level findings) |
| `evidence` | One to three sentences of fact: what was observed, with numbers where they exist. Name the collected artifact (file name or step number in the trace) |
| `confidence` | `high`, `medium` or `low` |
| `tester` | `human` or the model id of the AI that judged |

Rules:
- `failed` needs evidence that shows the failure; do not write it from a guess.
- `passed` means that this tester checked the criterion across the collected data and found no failure; it is not a conformance claim.
- `inapplicable` means the content the criterion is about does not exist on the page (state which content you looked for).
- `cantTell` means the data cannot decide it. Say what is missing and which pass or person could decide.
- One finding per element and criterion; do not merge different locations.

Example (JSON, one finding):

```json
{"criterion": "2.4.7", "outcome": "failed", "location": "https://example.org/form#nav a.skip", "evidence": "No visible change between focused and blurred crops at focus step 3 (focus-trace/step-03.png): outline is none, no replacement style.", "confidence": "medium", "tester": "claude-sonnet-5-5"}
```
