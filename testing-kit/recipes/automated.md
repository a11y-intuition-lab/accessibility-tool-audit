# Automated rule checks

> Status: AI-drafted, not human-reviewed

Group id: `automated`. Run two independent rule engines (axe-core and HTML_CodeSniffer through pa11y) over the page and store their raw output. This pass decides nothing by itself beyond what a rule can decide: a reported violation is a candidate failure, "incomplete" or a warning is a request for review, and a rule that did not fire is not evidence of a pass. It is the cheapest pass and runs first; its output feeds every later pass. No success criterion has full automation in our triage, so this group has no primary criteria.

## Setup

- Headless Chromium, viewport 1280 x 1024, device scale factor 1, light colour scheme, JavaScript on, no extensions, clean profile.
- axe-core, version pinned and recorded, all rule tags enabled: wcag2a, wcag2aa, wcag2aaa, wcag21a, wcag21aa, wcag22aa, best-practice, experimental.
- pa11y with the HTML_CodeSniffer runner, version pinned and recorded: main pass `WCAG2AAA` with warnings and notices included, supplementary pass `WCAG2AA` (D-024: the `WCAG2AAA` ruleset lacks some sniffs, such as the 2.2.1 meta refresh checks).
- Wait for the load event plus 2 seconds of network idle before running, so script-built content exists.
- AI capability needed: none for collection. A script does this pass. An AI only reads the stored output in the judging step.

## Collect

Collect all of this before judging. Each item names the data type (`needs` key in the data file). A script or a cheap model can do it without judgement; store each artifact with a file name that the report can cite.

1. **dom** — Load the URL, wait as described, then run axe-core on the whole page. Store the complete result object: `violations`, `incomplete`, `passes`, `inapplicable`, with node selectors and the rule's tags.
2. **dom** — Run pa11y with the `WCAG2AAA` standard, warnings and notices on, `ignore` list empty. Store every issue with `type` (error, warning, notice), `code`, `selector`, `message`.
3. **dom** — Run pa11y again with the `WCAG2AA` standard, same settings. Store separately.
4. **dom** — If the page links to or embeds other pages needed to judge a rule (for example frames or a linked example page), run both tools on those too and store per URL.
5. **screenshot** — Save one full-page screenshot at 1280 px so a reviewer can find the nodes the tools name.
6. **dom** — Record tool versions, browser version, viewport, settings and a timestamp in one environment record.

## Judge

Map each stored tool result to an outcome per success criterion with the rule-to-criterion table in the data file (`automation.rules`), never by reading a message and guessing.
- A tool `violation` (axe) or `error` (HTMLCS) on a rule mapped to the criterion: `failed`, confidence high for axe rules that decide the whole condition, medium for rules that only detect one failure pattern.
- axe `incomplete`, or an HTMLCS `warning`: `cantTell`. Pass the node and the reason to the later pass named in the criterion's primary group.
- HTMLCS `notice`: not evidence. It is a page-level reminder. Use it only to know that the element type exists.
- A rule that ran and passed: `passed` only for the exact condition the rule tests. Do not turn it into a `passed` for the whole criterion; all our criteria are partial or none.
- A mapped rule that returned nothing and no applicable nodes (`inapplicable`): record `inapplicable` for that rule, not for the criterion.
- Deprecated and best-practice rules (for example 4.1.1 duplicate ids, landmark rules) are reported, but tagged so the report shows they are not current WCAG 2.2 requirements.

Primary criteria: none. Criteria that a rule engine reports on, and that are primary elsewhere, are listed below only where their rule needs a note.

### 1.4.3 Contrast (Minimum) (AA)

Also checked in `visual` ([recipe](./visual.md)). Contrast of text on solid backgrounds: use axe `color-contrast`. A violation is `failed` (high). Text over images, gradients or overlaps returns `incomplete`: hand that node to the visual pass. Understanding: <https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html>

### 1.4.6 Contrast (Enhanced) (AAA)

Also checked in `visual` ([recipe](./visual.md)). As 1.4.3 with `color-contrast-enhanced` (7:1, 4.5:1 for large text). AAA; report it separately from 1.4.3 and mention that GOV.UK 2017 did not enable AAA tags. Understanding: <https://www.w3.org/WAI/WCAG22/Understanding/contrast-enhanced.html>

### 2.5.8 Target Size (Minimum) (AA)

Also checked in `pointer-motion` ([recipe](./pointer-motion.md)). axe `target-size` checks the 24 CSS px minimum and spacing. A violation is a candidate; exceptions (inline, equivalent control, user-agent control, essential) need the pointer-motion pass. Understanding: <https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html>

### 4.1.1 Parsing (A)

Also checked in `code-and-tree` ([recipe](./code-and-tree.md)). Removed in WCAG 2.2. axe `duplicate-id` and `duplicate-id-active` and HTMLCS F77 catch duplicate ids only; a fuller check needs an HTML validator (code-and-tree pass). Understanding: <https://www.w3.org/WAI/WCAG22/Understanding/parsing.html>

## AI and human

Taken from the data file (`ai.level`, `human.level`). Levels: AI likely/possible/unlikely; human must/should/optional.

- **1.4.3** Contrast (Minimum): AI likely (needs screenshot, dom); human optional. AI: Pixel sampling of rendered text plus computed styles covers the cases rules cannot compute. Human: Tools plus pixel-based AI checks suffice.
- **1.4.6** Contrast (Enhanced): AI likely (needs screenshot, dom); human optional. AI: Pixel sampling covers what rules cannot compute. Human: Tools plus AI suffice.
- **2.5.8** Target Size (Minimum): AI likely (needs dom, screenshot); human optional. AI: Target geometry is computable. Human: Tools plus AI suffice.
- **4.1.1** Parsing: AI likely (needs dom); human optional. AI: Parsing errors are mechanical. Human: Tools suffice; consider adding a validator.

## Report

Write one finding per criterion and location. Use exactly these fields.

| Field | Content |
|---|---|
| `criterion` | Success criterion id, for example `1.4.3` |
| `outcome` | `failed`, `passed`, `inapplicable` or `cantTell` |
| `location` | Page URL plus CSS selector of the element (or `page` for page-level findings) |
| `evidence` | One to three sentences of fact: what was observed, with numbers where they exist. Name the collected artifact (file name or step number in the trace) |
| `confidence` | `high`, `medium` or `low` |
| `tester` | `human` or the model id of the AI that judged |

Rules:
- `failed` needs evidence that shows the failure; do not write it from a guess.
- `passed` means that this tester checked the criterion across the collected data and found no failure; it is not a conformance claim.
- `inapplicable` means the content the criterion is about does not exist on the page (state which content you looked for).
- `cantTell` means the data cannot decide it. Say what is missing and which pass or person could decide.
- One finding per element and criterion; do not merge different locations.

Example (JSON, one finding):

```json
{"criterion": "2.4.7", "outcome": "failed", "location": "https://example.org/form#nav a.skip", "evidence": "No visible change between focused and blurred crops at focus step 3 (focus-trace/step-03.png): outline is none, no replacement style.", "confidence": "medium", "tester": "claude-sonnet-5-5"}
```
